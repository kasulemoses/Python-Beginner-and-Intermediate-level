## Learning goals

Combine schemas, routing, persistence, errors, and a frontend into complete CRUD workflows.

Follow the [setup guide](../python_for_web/README.md), configure MongoDB, seed the fictional records, and start both servers. Read Days 26–28 first.

## The contract

| Method | Endpoint | Result |
| --- | --- | --- |
| GET | /api/v1/students | items, total, offset, limit |
| POST | /api/v1/students | 201 with created student and Location header |
| GET | /api/v1/students/{id} | one student, or 404 |
| PATCH | /api/v1/students/{id} | updated student; only supplied fields change |
| DELETE | /api/v1/students/{id} | 204 with no body, or 404 |

Query options: exact country match, offset >= 0 (maximum 100,000), and limit 1–100 (default 10). Sorting is by name then _id so equal names have deterministic order. total and items are separate reads; concurrent writes may change the count between them.

The new API version path is /api/v1. The old /api/v1.0 tutorial URL is retired; no existing deployed client was identified or modified.

## Schemas protect the boundary

Read [schemas.py](../python_for_web/backend/app/schemas.py):
- StudentCreate requires name, country, city, and date_of_birth; skills and bio have defaults.
- StudentUpdate accepts a nonempty subset of editable fields.
- StudentRead adds string id and UTC creation/update timestamps.
- Unexpected fields are rejected; null is not accepted for student fields.
- Names and locations cannot be blank. Date of birth cannot be in the future.
- Skills are trimmed, bounded, and deduplicated; [] clears the list. An empty bio clears the bio.

Creation dates and IDs are generated by the server, not supplied by clients.

## Create a record

```sh
curl -i -X POST http://127.0.0.1:8000/api/v1/students \
  -H 'Content-Type: application/json' \
  -d '{"name":"New Learner","country":"Uganda","city":"Kampala","date_of_birth":"2000-01-01","skills":["Python"],"bio":"Fictional exercise profile"}'
```

Copy the returned id for subsequent calls. A successful creation returns 201 and Location. The server converts the MongoDB ObjectId into an ordinary string for the frontend.

## Read and paginate

```sh
curl 'http://127.0.0.1:8000/api/v1/students?country=Uganda&offset=0&limit=10'
```

Use /docs to call GET /students/{id}. A malformed ObjectId returns 422. A valid ID with no record returns 404. Single-item retrieval returns an object, not a list.

## Partial updates

In /docs, send PATCH with just:

```json
{"city":"Jinja","skills":["Python","React"]}
```

The application uses model_dump(exclude_unset=True) and MongoDB $set. name and date_of_birth remain unchanged, created_at is preserved, and updated_at advances. An empty request or a null field is rejected.

A plain document is not an update operator document: update_one needs an operator such as $set. Use replace_one only when you intend replacement. This API implements PATCH; PUT is not supported.

## Delete

Use DELETE /students/{id} in /docs. Success is 204 with no response body; fetching or deleting the same record again returns 404. The frontend asks for confirmation before deletion.

Do not practice on real student records. No delete-all or drop-collection endpoint is provided.

## Follow the implementation

[main.py](../python_for_web/backend/app/main.py) owns HTTP validation, response models, and errors. [students.py](../python_for_web/backend/app/students.py) owns MongoDB operations. Routes receive a repository dependency, which allows isolated tests and real database integration checks.

PyMongo errors return a safe 503 message. /health checks that the API is running; /ready performs a bounded storage query. Analysis stays usable without student storage.

The Next.js directory page supports creation, details, edits, deletion, exact-country filtering, pagination, loading, empty states, and visible errors. Failed saves preserve input. It uses the same API contract as Swagger UI.

## Tests and exercises

From python_for_web/backend:

```sh
.venv/bin/python -m pytest -q
```

The setup guide explains MONGODB_TEST_URI for integration tests. Those tests use random disposable database names and clean up only their own databases.

1. Create → read → edit → delete through /docs, then repeat through the frontend.
2. Patch only city; prove that name and created_at remain unchanged.
3. Try {}, null, a future birthday, unknown fields, and an invalid ID.
4. Add more than ten fictional learners and verify pagination and country filtering.
5. Stop MongoDB while the API is running. Compare /health, /ready, and student endpoint responses.
6. Run browser tests on desktop and mobile viewports.
7. Design authorization rules before extending this local demo to public writes.

**You are finished when:** workflows pass against real MongoDB, invalid input cannot silently alter records, errors are understandable, and the frontend production build succeeds.
